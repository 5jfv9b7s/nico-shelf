# v0.19.0 公開ベータへの適用と確認

この版は公開前の保護・説明・検証手段を追加します。ZIPを置くだけで本番が検証済みになるものではありません。まず個人利用の環境へ適用し、以下の本番確認を終えてから案内します。

## 適用順

1. 現行のJSONバックアップを保存し、DBのバックアップ方法を確認します。SQLはDB所有者で実行します。
2. Supabase SQL Editorで `supabase/migrations/202611190001_public_readiness.sql` を**ファイル全体**実行します。v0.17.3までのSQLが前提です。文字化けを防ぐためASCIIだけで記述しています。最後に `usage_rpc_ready = true` を確認します。
3. 更新ZIPを既存プロジェクトへ上書きし、`npm ci`。最新版の `wrangler.jsonc` を含めます。そこには公開用Supabase URLと2つのレート制限バインディングを保持しています。シークレットは含みません。Render側の変更はありません。
4. 個人利用では従来どおり `npm run build` でビルドできます。一般公開するビルドでは、下の追加環境変数を設定し、`npm run check:release` と `npm run build` を実行します。
5. CloudflareへWorkerとアセットをデプロイします。環境変数はビルド用とランタイム用を混同しないでください。
6. 以降の監査・2アカウント・画面・復元確認を行い、記録します。問題があれば一般向け告知は保留します。

`SQL`は既存の曲・メモを削除しません。上限を超える既存データも保持します。再実行できますが、使用量を再集計する間は5テーブルの書き込みをロックするため、利用の少ない時間に実行してください。古いクライアントにもDB上限が効きます。

## 追加するビルド環境変数

| 名前 | 値 | 保存先 |
| --- | --- | --- |
| `VITE_OPERATOR_NAME` | 公開できる運営者名または活動名 | Cloudflareのビルド環境変数 |
| `VITE_SUPPORT_URL` | 自分が確認できるHTTPS問い合わせフォームURL、または `mailto:` メールアドレス | 同上 |
| `NICO_PUBLIC_LAUNCH` | 一般公開するビルドでは `1` | 同上 |

既存の `VITE_SUPABASE_URL` と `VITE_SUPABASE_PUBLISHABLE_KEY` も必要です。値は生成された公開ページに入るため、公開してよいものだけを指定します。フォームを使う場合は、登録アカウントのメールアドレス、依頼内容、返信方法を扱えるよう運営者自身が設定してください。ここではフォームの新規作成・送信は行いません。

`NICO_PUBLIC_LAUNCH=1` で運営者名・連絡先・公開Supabase設定が不足すると、ビルドが失敗します。個人利用のビルドを維持するため、未設定時に全ビルドを止める方式にはしていません。**`check:release`は設定の存在確認だけで、本番の安全性を判定するコマンドではありません。**

`SUPABASE_URL`、`PUBLIC_MYLIST_SOURCE`、ゲートウェイURLはWorkerのランタイム変数です。`SUPABASE_JWT_SECRET`（HS256の場合）とゲートウェイ共有トークンは既存のWorkerシークレットに保持します。`VITE_`へ入れないでください。問い合わせ先の変更後は再ビルドが必要です。

## 保存上限

| 対象 | 1アカウントの初期上限 |
| --- | ---: |
| 動画 | 10,000件 |
| マイリスト | 50件 |
| リストへの所属 | 30,000件（`present=false`の履歴も含む） |
| メモ・評価行 | 10,000件 |
| 保存検索 | 20件 |
| 論理データ量の合計 | 50 MiB |

サービス全体の論理データ量は250 MiBが初期上限です。既存の超過データを削除せず、その上限を超える増加を拒否します。件数超過時も更新・削除は可能です。文字列や容量の超過時は、同じ長さ以下の保存と削除を許可します。

文字数の主な上限は曲名1,000字、説明20,000字、メモ10,000字、リスト名200字です。動画の各配列は100要素・16 KiB、保存検索のフィルターは8 KiB、1行は64 KiBまでです。旧スナップショットRPCの曲名220字など、既存のより小さい制限は維持しています。

DBトリガーが通常のREST書き込み・RPCの両方に適用されます。同一SQL文／同期RPCは上限エラーで全体がロールバックします。ファイル取り込みは複数リクエストに分かれるため、先に成功したチャンクは残ります。画面とヘルプにもこの点を表示します。黙って超過分を切り捨てません。

使用量は各行のJSON文字列表現のUTF-8バイト数です。実ディスクの厳密な大きさではありません。インデックス、Auth、ログ、トランザクション履歴、基盤の固定領域等は含まず、**料金やDB容量の絶対的な上限を保証しません**。管理者・service_roleはRLSを迂回するため、アプリに管理キーを置いてはいけません。SQL Editorでの通常INSERTにもトリガーは効きますが、管理者によるトリガー無効化・TRUNCATE等は使用量を壊します。

小規模ベータ用に全体使用量の1行で課金処理を直列化しています。公開人数・更新頻度が増えた場合は、待ち時間と実容量を観測して方式と上限を再評価してください。デッドロック等の失敗を自動成功扱いにはしません。ローカルPGliteのテストは単一DB接続で、本番複数セッションの負荷試験は含みません。

## 読み取り専用の本番監査

Supabase SQL Editorで `supabase/audits/public_readiness.sql` を実行します。書き込み・修復は行いません。

- 5テーブルでRLS有効。anonの権限はなく、authenticatedはCRUDのみでTRUNCATE権限なし。
- ポリシーに想定外の許可がない。いずれも本人の `auth.uid() = owner_id` を確認。
- 5つの `nico_library_limits` トリガーが有効。
- スナップショットRPCはinvoker、使用量RPCと上限トリガーはdefiner。固定された空のsearch_pathで、privateスキーマへの一般ユーザー権限がない。
- 使用量不一致クエリが0行。既存データが上限超過していた場合は、削除せず状態を記録して運用を決める。
- 論理使用量とは別にDBの実容量とAuthユーザー数を見る。

監査結果には利用者のUUIDや件数が含まれます。広く公開せず、エラーの相談には不要な情報を伏せてください。不一致が出た場合は原因を確認し、勝手にカウンターをゼロへ直さないでください。

## 本番の2アカウント検証

初めてログインした**別々の空のテストアカウント**を2つ用意します。普段のライブラリを使わないでください。スクリプトも既存データがある場合は拒否します。

`verify-production.mjs` は各アカウントにランダム印のテストデータだけを作り、次を確認してfinallyで削除します。

- 未ログインでは5テーブルと使用量RPCへのアクセスが拒否される。
- 自分の行は読め、相手の行は読めない。相手への更新・削除は0行またはRLS拒否。
- 相手のowner_idを指定したINSERTが `42501` で拒否される。単なる重複・外部キーエラーを合格としない。
- 使用量RPCが自分の件数だけを返す。テスト後は両アカウントのライブラリ・使用量が空。

Node 22.13以上。プロジェクト直下に `.env.verify.local` を作り、以下の名前を設定します。このファイルはgitignore対象です。トークンはブラウザのログインセッションから**自分のPC上だけ**で取得・保存し、短時間で検証して削除します。チャットやGitHubへ貼り付けないでください。管理キーやrefresh tokenは使いません。

```dotenv
NICO_VERIFY_TEST_ACCOUNTS=1
VERIFY_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VERIFY_SUPABASE_PUBLIC_KEY=YOUR_PUBLISHABLE_OR_ANON_PUBLIC_KEY
VERIFY_ACCESS_TOKEN_A=TEST_ACCOUNT_A_ACCESS_TOKEN
VERIFY_ACCESS_TOKEN_B=TEST_ACCOUNT_B_ACCESS_TOKEN
```

```bash
node --env-file=.env.verify.local scripts/verify-production.mjs
```

空のテストアカウントにログインしているアプリの開発者ツールConsoleから、ローカルでセッションを確認する場合は次を使えます。tokenをConsoleへ出力するため、画面共有・録画中は実行しないでください。

```js
const sessionKey = Object.keys(localStorage).find((key) => key.startsWith('sb-') && key.endsWith('-auth-token'));
const testSession = JSON.parse(localStorage.getItem(sessionKey));
testSession.access_token;
```

プロジェクトによって保存形式・キー名が異なる場合は、該当する自分のテストセッションを確認します。取得対象を間違えないでください。有効期限が切れた場合は再取得します。スクリプトはアクセストークンをログに出しません。

途中で中断・通信失敗した場合、`.nico-verify-manifest.json` が残ります。削除せず同じ2アカウントで次を実行します。ランダム印に一致するテストデータだけが対象です。

```bash
node --env-file=.env.verify.local scripts/verify-production.mjs --cleanup
```

両方のPASSを確認し、ローカルのトークン設定ファイルを削除します。この検証はSQL Editorの所有者権限でのSELECTとは異なり、実際の公開キー・ユーザーJWT・REST経由で行います。ここで配布した版では、本番での実行はまだ行っていません。

## 画面と認証の本番確認

- 未ログインで `/help.html`、`/privacy.html`、`/terms.html` を開け、連絡先が実際に届くことを確認する。運営者が内容を読み、自分の保存・問い合わせ・削除運用と一致させる。
- Googleログインの本番URL、許可したリダイレクト先、表示される同意画面を確認する。Googleの認証プラットフォームにホームページとプライバシーURL・利用条件URLを登録し、必要な公開設定・審査の表示を確認する。必要なスコープだけを要求する。
- 新規ユーザーで初回ログイン→空画面→取り込みプレビュー→保存→再ログイン→他端末で表示が維持されること。
- 公開マイリストを実際に取得する。`/api/public-mylists/status` の正常応答だけではニコニコとの実通信成功を確認したことにならない。既知の499/500件リストでは部分取り込みの案内と既存所属の保持を確認する。
- 360px前後のスマホ幅で、下部ナビ、取り込み画面、使用量表、分析結果、問い合わせページを確認する。
- 別アカウントへ切り替えた際に、以前のライブラリ・メモ・分析結果・使用量が残らないこと。

## バックアップ・削除・運用

1. **利用者JSONの復元試験**：元のアカウントでバックアップを保存し、別の空のテストアカウントへ取り込む。曲数、所属履歴、メモ、評価、保存検索の件数と代表値を照合する。JSONはAuth登録・運営全体のDBバックアップを含まない。
2. **DBのバックアップ**：Supabaseのプランとダッシュボードで利用可能なバックアップ・保存期間を確認する。必要に応じて公式CLIの `db dump` 等で別途エクスポートし、暗号化した保管先に保存する。ここでは定期実行・オフサイト保管を設定していない。
3. **DBの復元試験**：別のSupabaseプロジェクト等の隔離環境へ復元し、RLS・RPC・使用量を確認する。本番への上書き復元を試験として実施しない。AuthやStorageなど、DBダンプだけでは戻らない対象を区別する。
4. **登録情報削除依頼**：連絡先で依頼元の本人確認を行い、必要なバックアップ確認後、SupabaseのAuthentication管理画面で対象ユーザーを正確に確認して削除する。ライブラリは外部キーで連動削除される。Auth登録情報の自己削除APIは今回追加していない。バックアップ・ログに残る範囲も、実際の基盤設定に従って説明する。
5. **運用監視**：少人数の間は日次を目安に、Cloudflareのエラー・429/503件数、Renderの稼働・上流拒否、SupabaseのDB実容量・Authユーザー増加を確認する。メモ本文・Cookie・認証トークンは監視ログへ追加しない。連携先障害で削除扱いしない挙動を維持する。
6. **外部取得の制約**：非公式APIのため停止・欠落を想定し、JSON・従来連携を案内する。ニコニコ本体への書き込み連携は引き続き対象外。一般公開時の取得用途・頻度と連携先の利用条件は運営者が確認する。

`/health`（Render）はサーバーの応答確認で、ニコニコ取得の正常性を保証しません。監視通知、料金アラート、定期バックアップは管理アカウントからの設定が必要で、このZIPだけでは有効になりません。

## 検証範囲

ローカルではPGliteで全マイグレーションを実行し、RLSのCRUD・匿名拒否・外部キー、所有者限定RPC、件数/文字/容量上限、更新・削除・Auth削除カスケード、上限時のRPCロールバック、再適用と既存データ保持を検証します。PGliteはPostgreSQL互換の実行環境ですが、Supabase本番固有の権限変更や設定までは再現しません。
