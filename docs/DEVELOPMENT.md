# 開発ルール

## 命名・コメント

- ファイル名・関数名は、機能が伝わる英語にする（`countLibrary`、`registerEventHandlers`）。
- 略語一文字の変数は、狭いスコープのループなどを除いて避ける。
- コメントは主に **なぜその処理が必要か・変更すると何が危険か** を書く。
- 非公開APIの使用箇所には、取得失敗時と仕様変更時の扱いを記載する。
- Supabaseへの書き込み処理には、対象テーブルとアカウント分離条件を意識する。

## フォーマット

```bash
npm install
npm run format        # Prettierで整形（初回は差分が大きくなる）
npm run format:check  # 整形済みか確認
```

`.editorconfig` と `.prettierrc.json` に基準を定義しています。今回の版では、古いHTMLテンプレートすべてを一括整形していません。**整形だけのコミットを機能変更と混在させない**ことを推奨します。

## テスト

```bash
npm test
node --check src/main.js
npm run build
```

- 画面：検索、ソート、名寄せ、重複表示、HTMLエスケープを確認する。
- 登録：重複許可、満杯のリスト、「最近のお気に入り」を自動選択しないことを確認する。
- 同期：件数一致だけでなく動画ID差分で確認し、途中失敗を成功と扱わない。
- メタデータ：既存の手動入力・メモ・評価を消さない。
- 変更前に `npm test`、変更後にも `npm test` を実行する。

## 開発・デプロイ時の秘密情報

- `VITE_SUPABASE_URL` と `VITE_SUPABASE_PUBLISHABLE_KEY` は公開クライアント情報。
- `service_role` / secret key、Google OAuthのClient Secret、Cookie、トークンはGitHub・Vite環境変数へ入れない。
- 実データ（マイリストや個人的なメモ）をテストファイルへ埋め込まない。
- SQLマイグレーションを変更した場合はRLSと本人以外のデータが読めないことを別アカウントで確認する。

## コミットの粒度（推奨）

1. 純粋なリファクタリング（出力・機能を変えない）
2. フォーマットのみ
3. 機能追加とそのテスト
4. API・DBスキーマ変更と移行手順

変更が多い場合ほど小さく分けてレビュー可能にします。
